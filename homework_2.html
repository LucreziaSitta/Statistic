Step 0 · BIP-39
Random entropy and the mnemonic words
key generationencodingchecksum

Everything starts from a random number. This is the only real key generation in the whole pipeline: all the next steps are deterministic. BIP-39 takes 128 random bits, adds a small checksum (the first 128/32 = 4 bits of SHA-256 of the entropy) and cuts the 132 bits into 12 groups of 11 bits. Each group is a number from 0 to 2047, i.e. one word of a fixed list of 2048 words. The words are just an encoding of the bits that is easier to write on paper.

Step 1 · BIP-39 · PBKDF2
Mnemonic → 512-bit seed
key derivation

The words are not used directly as a key. They go through PBKDF2 with HMAC-SHA512, repeated 2048 times, with the salt "mnemonic" + passphrase. The result is a 512-bit seed. The repetitions make every guess slower for an attacker, and the optional passphrase gives a completely different wallet from the same words.

Step 2 · BIP-32 + BIP-44
Seed → private key
key derivation

BIP-32 turns one seed into a whole tree of keys. First HMAC-SHA512 with the key "Bitcoin seed" gives the master private key (left 256 bits) and a chain code (right 256 bits). Then each child key is computed from its parent with HMAC-SHA512 again. BIP-44 fixes which branch to use: m / purpose' / coin' / account' / change / index. The apostrophe means "hardened": that level uses the parent private key, so a leaked child key cannot be used to go back up the tree.

Step 3 · secp256k1
Private key → public key
public-key cryptography

This is exactly Homework 1, with real numbers: Q = k·G on the curve y² = x³ + 7, but modulo a 256-bit prime p instead of 17, computed with double-and-add. The private key k stays secret; Q can be shown to everybody, because going back from Q to k (the discrete logarithm problem) would take about 2¹²⁸ operations.

Step 4 · Keccak-256
Public key → address
hashing

The public key is 64 bytes (x and y), too long to share easily. Ethereum hashes it with Keccak-256 and keeps only the last 20 bytes of the 32-byte hash. The address is therefore a fingerprint of the public key: shorter, fixed in length, and it reveals the public key only after the first transaction.

Step 5 · EIP-55
Address → checksummed address
checksumencoding

Hex addresses are case-insensitive, so the case of the letters a–f is "free" information. EIP-55 uses it as a checksum: we hash the lowercase address (as text) with Keccak-256, and every letter whose matching hash digit is 8 or more is written in UPPERCASE. A wallet that receives a mixed-case address recomputes the pattern: if one character was mistyped, the pattern almost certainly no longer matches.

3. The six standards and what each one is for
For each standard we asked: what problem was it trying to solve?

generationencodingchecksumderivation
BIP-39 · mnemonic and seed. A 128-bit number written in hex (32 characters) is very easy to copy wrong. BIP-39 encodes it as 12 common words (11 bits each, 2048 = 2¹¹ words, the first 4 letters of each word are unique), adds a checksum so most mistakes are caught, and stretches it into a 512-bit seed with PBKDF2.

derivation
BIP-32 · hierarchical deterministic keys. Early Bitcoin wallets generated every key at random, so each new address needed a new backup. BIP-32 derives an unlimited tree of keys from one seed: child = (parent + HMAC-SHA512(chain code, data)) mod n. Normal children can be computed from the parent public key (useful for watch-only wallets), hardened ones only from the private key, which is safer.

derivation
BIP-44 · standard paths. BIP-32 allows any path, so two wallets could show different addresses for the same seed. BIP-44 fixes m / 44' / coin' / account' / change / index. Coin type 60 is Ether (0 is Bitcoin); on Ethereum "change" is always 0.

public-key
secp256k1. It links k and Q = k·G and it is the curve of the ECDSA signatures of every transaction. With ~256-bit keys it gives about 128-bit security, while RSA needs about 3072-bit keys for a similar level: smaller keys and signatures matter on a blockchain where everything is stored forever. Ethereum took it from Bitcoin, which picked it from the SEC 2 standard.

hashing
Keccak-256. It turns the 64-byte public key into the 20-byte address and is used almost everywhere else in Ethereum (transaction hashes, contract storage, EIP-55). We rely on it being fast, impossible to invert and with a strong avalanche effect. It is the original Keccak, not exactly NIST SHA3-256 (card 8).

checksumencoding
EIP-55. Plain hex addresses have no error detection: one typo sends money to a different valid-looking address. EIP-55 uses the letter case as checksum bits and stays backward compatible, because old software reads addresses in lowercase. It detects mistakes, not attacks.
4. Five different jobs
The assignment asks to keep these concepts separate. For each step we asked: does it create something new or compute it from something existing? and can it be reversed?
ConceptWhat it doesWhereReversible?
key generationCreates new secret randomnessThe random bits of step 0 (only here)Starting point
key derivationComputes keys deterministically from secret materialPBKDF2, BIP-32, BIP-44No (HMAC is one-way)
public-keyKey pair linked by a hard problem; signaturessecp256k1: Q = k·G, ECDSAOnly with the private key
hashingFixed-length fingerprint, no keyKeccak-256, SHA-256 (BIP-39 checksum), SHA-512 in HMACNo
checksumExtra bits to catch accidental mistakesLast 4–8 bits of the mnemonic, EIP-55 letter caseOnly says valid / not valid
encodingSame information, different representationBits → words, bytes → hex, mixed caseYes, always
A common confusion is between hashing and encoding: hex or the 12 words can always be converted back, while from the address it is impossible to get back to the public key. Another one is between checksum and hash: EIP-55 uses a hash, but its goal is only to catch typos.
5. Statistical exploration (random wallets)
We generate many random wallets and look at the outputs. Same question as in Homework 1: which properties should we expect, and which ones matter for security? Here the results are very different from the toy curve, because the address goes through a hash function.
N =
a) BIP-39 checksum: how many random word lists are valid?
12 random words pass the 4-bit checksum by chance with probability 1/16 = 6.25%; 24 words (8 bits) with 1/256 ≈ 0.39%. So a wrong word is detected 15 times out of 16.
b) Hex digits of the addresses (χ² test)
If the hash behaves like a random function every hex digit has probability 1/16. χ² test with 15 degrees of freedom (critical value ≈ 25.0 at 5%). Every cell has hundreds of expected observations, so unlike Homework 1 the test is reliable.
c) Are 0s and 1s balanced?
We write all the addresses in binary and count the 1s. If the hash output looks random, about half of the bits should be 1, and that is what we get.
d) Avalanche: flip one bit of the public key
We count how many of the 256 Keccak output bits change. For an ideal hash: Binomial(256, ½), mean 128, standard deviation 8 (green line). In Homework 1 the change was predictable (Q ± 2ⁱ·G); after the hash it looks random.
e) Avalanche through the whole pipeline: flip one bit of the private key
The two public keys are related (they differ by 2ⁱ·G), but the hash hides it: about 80 of the 160 address bits change, Binomial(160, ½), standard deviation ≈ 6.3.
f) EIP-55: how many checksum bits does an address have?
Only letters a–f carry the checksum. Each hex digit is a letter with probability 6/16, so the number of letters is Binomial(40, 3/8): 15 checksum bits on average, but it varies from address to address.
g) EIP-55: does it catch typos?
We replace one random character with a different hex digit. The typo changes the whole Keccak hash, so the new case pattern is random: it passes only if all L letters happen to have the right case, probability (½)ᴸ ≈ 2⁻¹⁵ on average. Without the checksum every typo goes through.
6. Which statistical properties matter, and where
  • Uniform digits and balanced bits (b, c) are what we expect from a good hash: the address should not leak anything about the key. But passing these tests does not prove security, a non-secure function can also produce balanced bits.
  • Avalanche (d, e) is a hash property. secp256k1 alone does not have it (Homework 1), the full pipeline does because Keccak-256 comes after it.
  • Checksum statistics (a, f, g) are about error detection, not security: 4 bits for BIP-39 and ~15 bits for EIP-55 catch accidental mistakes, but an attacker can easily search for a fake address with a valid checksum.
  • Entropy is decided only at step 0: 12 words = 128 bits, 24 words = 256 bits. No later step can add randomness.
7. Timeline: how we got here
Filled dots are the dates asked in the assignment, empty ones are extra context.
  • 1976Diffie and Hellman publish the idea of public-key cryptography.
  • 1977RSA: the first practical public-key system, based on the difficulty of factoring large numbers.
  • 1985Koblitz and Miller independently propose elliptic-curve cryptography: same security with much smaller keys.
  • 2000The SEC 2 document lists the curve secp256k1.
  • 2001SHA-2 (SHA-256, SHA-512) standardized by NIST. SHA-256 is later used in the BIP-39 checksum, SHA-512 inside HMAC for BIP-32 and BIP-39.
  • 2009Bitcoin launches using secp256k1.
  • 2012BIP-32: one seed for a whole tree of keys. The same year Keccak wins the NIST SHA-3 competition.
  • 2013BIP-39: the seed can be written as 12–24 words.
  • 2014BIP-44: standard paths, so different wallets find the same accounts.
  • 2015Ethereum launches (July) using Keccak-256 as submitted to the competition.
  • 2015SHA-3 published by NIST (FIPS 202, August), based on Keccak but with a different padding.
  • 2016EIP-55: mixed-case checksum addresses.
The order explains a lot: Ethereum reused the wallet standards Bitcoin had already developed (BIP-32/39/44, secp256k1) and only changed what was specific to it, the hash and the address format. And since Ethereum started just before SHA-3 was finalized, it kept the original Keccak.

9. Why several techniques instead of one algorithm?
Each step needs a property that the others don't have, and no single algorithm has all of them:
  • BIP-39 / BIP-32 / BIP-44 → key management. The problem is human: backing up and recovering many keys. We need something deterministic (same words, same keys), readable and compatible between wallets. A hash alone could derive keys, but not the tree structure or the standard paths.
  • secp256k1 → public/private relationship. Only public-key cryptography lets everyone verify a signature without being able to create it. A hash has no "public" and "private" side. It is also the only step where we want algebraic structure (Homework 1).
  • Keccak-256 → hashing. A short, fixed-length identifier that hides the structure of the public key, which secp256k1 alone keeps (we saw it with the avalanche test).
  • EIP-55 → error detection. A completely different goal: protecting against human mistakes when copying addresses, at zero cost and backward compatible.
It is the same principle as in software engineering: each component does one job well. It also limits damage: if one primitive were broken (for example the ECDLP by a quantum computer), addresses that never sent a transaction would still hide their public key behind the hash.
10. Trying it with a real wallet
The easiest experiment is to import the public test phrase "test test test test test test test test test test test junk" in a wallet such as MetaMask (on a separate browser profile, never for real funds) and compare its accounts with card 1: they match, because MetaMask uses the BIP-44 path m/44'/60'/0'/0/i and increases i for each new account. Other things we noticed:
  • Wallets ask to write the 12 words in order and check them: that is the BIP-39 checksum and encoding at work.
  • Copied addresses are always in mixed case: that is EIP-55. Changing one letter by hand usually makes the wallet show a warning.
  • Not every wallet uses the same path: some, for example hardware-wallet apps, increase the account level instead of the last index, so the same phrase can show different accounts, the problem BIP-44 tried to solve.
  • Some wallets support the passphrase ("25th word") and some don't: with a passphrase the same words open a completely different wallet (try it in the side panel).
